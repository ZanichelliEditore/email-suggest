Decompose a phase of `SPEC.md` §13 into session-sized tasks. Argument: the phase (e.g. "Phase 2").

1. Read `AGENTS.md`, `docs/tasks/PLAN.md`, and the `SPEC.md` sections that the phase's acceptance criteria reference. Read `SPEC.md` §14.1 for the sizing heuristic.
2. Use the `planner` sub-agent (read-only) to propose a decomposition. You, the main session, write the result.
3. For each task: id in the form `T-NNN` (continue numbering), title, type (`build | spike | port | plan`), depends-on, spec sections to read (at most three), files expected to change, one-line acceptance test. Size every task to fit in about half a context window; when in doubt, split. For a task likely to outgrow a session anyway, draw its split point now, in its task file, and count it in PLAN's sizing calibration.
4. Order tasks so that every task leaves `make quality` green, and by the project's safety core, which is: none.
   - Unless that answer is `none`, the safety core and its tests come before any code that could call it.
   - With `none`, an RFC that decides whether a safety core is needed comes before any task that would give the project its first genuinely dangerous capability; if the RFC adds one, it lands before that capability's first caller. `none` is an honest answer: never invent a safety core to fill the slot.
5. Write the tasks into `docs/tasks/PLAN.md` under the phase heading, and create one `docs/tasks/<id>-<slug>.md` per task from `docs/tasks/_template.md`, with status `todo` and `Created:` from `date +%F`.
6. This command is the only one that may reorder, re-scope, merge, drop or change the dependencies or acceptance of existing rows; `/handoff` may only update the current task's status and add `proposed` rows, except at the end of a `plan` task, where the planning authority carries through the handoff.
   One exception: an RFC the owner has accepted in-session may amend the acceptance of the rows it governs, in the commit that makes it Active. The decision is the authority, and a row that restates it out of date is drift. It may amend an acceptance line and nothing else: adding, dropping, reordering or re-scoping a row, or changing a dependency, stays with this command, and anything the RFC wants beyond an acceptance line it governs is a `proposed` row. The amendment must land in every place the acceptance is written (the `PLAN.md` row *and* the task file) and say in the RFC which rows it touched.
7. Present the plan to the owner as a table (id, title, type, depends-on, acceptance) and ask for review. Do not start any task. The owner may resize, merge or split tasks before giving the go.
8. Once the owner approves, run `/handoff`: it commits the plan and writes HANDOFF.md, so the next session's `/resume` finds a clean tree and the first task. A plan left uncommitted is a mismatch there.
